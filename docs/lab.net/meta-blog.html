Executable networking articles

The network design becomes the story

A detailed fabric definition can serve as both a design experiment and the executable example in a technical article. Here is how the eBGP blog connects topology, protocol state, and reader interaction.

Define the network before writing the walkthrough

The eBGP lab is a YAML .xp document. Its topology declares two routers in different autonomous systems and a client behind each. This abbreviated definition captures the network:

topology:
  device: frr
  module: [bgp]
  nodes:
    r1: {bgp: {as: 65001}}
    r2: {bgp: {as: 65002}}
    client1: {device: linux, role: host}
    client2: {device: linux, role: host}
  links: [r1-r2, client1-r1, r2-client2]

The loader allocates addresses, derives interfaces and loopbacks, and resolves BGP neighbors. Client-facing subnets are advertised into BGP; hosts receive default routes toward their attached routers. The source can also specify address pools, interface attributes, and protocol settings when those details are part of the experiment.

For a larger design, the fabric module expands leaf and spine counts, tier settings, pods, and racks into nodes and links. Define the AS allocation, loopbacks, client attachments, and overlay settings upfront. That produces a concrete fabric against which to test failure scenarios and alternative peering arrangements.

Run the protocols and inspect the result

Starting the embedded lab loads the WebAssembly engine and instantiates the topology. JavaScript coordinates the simulation and browser interface; the C/WASM core provides protocol and forwarding functionality. In this example, routers execute BGP through the JavaScript/WASM runtime, while clients use JavaScript host behavior.

BGP exchanges populate routing state, and traffic tests use the resulting forwarding tables. Packet events feed the link badges and message history. The article displays session state and installed-route counts separately, allowing readers to relate an established adjacency to the routes it supplies and the traffic those routes carry.

The runtime advances simulated time and supports pause, reset, and link changes. In the example below, start the lab and ping client2. Disable the router-to-router link, then repeat the ping. Restore it and observe the session and reachability recover.

Embed the lab and connect the prose to its state

The custom element loads a lab definition and provides the topology view and execution controls:

<script type="module" src="./embed.js"></script>
<lab-embed src="./examples/ebgp-icmp/lab.xp"></lab-embed>

For custom article controls, import the module before accessing the element’s session. This is the same API used by the eBGP page:

import './embed.js';

const session = document.querySelector('lab-embed').session;
session.subscribe('summary', summary => {
  // Render summary.state, summary.sessions, and summary.nodes.
});
session.subscribe('packet', event => {
  // Add protocol messages to the article’s event history.
});

// Call from a button after the lab has started.
const result = session.ping({
  node: 'client1', target: 'client2', count: 1
});

An iframe can embed the standalone topology instead: embed.html?lab=examples/ebgp-icmp/lab.xp. This page embeds the complete blog.html article so its custom readouts remain available too.

Make the scenario’s expectations explicit

The lab’s validate section describes expected device state and packet responses. For example, this check requires r1 to install the remote client subnet through r2:

validate:
  - label: r1 learns the remote client subnet
    state:
      - node: r1
        routes:
          - prefix: client2.prefix
            protocol: bgp
            nexthop: r2.ipv4.r1

References such as client2.prefix follow the allocated topology, so checks survive addressing changes. The full example also checks BGP session state, host default routes, an ICMP reply, and completion of an MRC RDMA Write. These declarations support validation workflows; the embedded article exposes its own ping button through the session API.

In a redundant fabric, extend the investigation to a leaf–spine failure: check which prefixes remain installed, whether next hops change, and whether clients can still communicate. A dual-homed client adds an attachment-failure scenario. EVPN/VXLAN and SRv6 designs introduce further questions about overlay reachability and forwarding paths. Each walkthrough can pair a specific configuration choice with a state check and a traffic test.

The published artifact then contains the topology that supports the explanation, the controls needed to reproduce the experiment, and the source for readers who want to change it.
